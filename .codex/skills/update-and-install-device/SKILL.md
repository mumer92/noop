# Update from main and install on the physical iPhone

This repo (`NoopApp/noop`, the Strand/NOOP app) is maintained by the team, but this machine
builds a **personalized** variant: a different Apple ID / signing identity, and a couple of
home-screen tweaks. None of that is committed upstream, so every time we catch up to the team's
`main` we have to carry (or re-derive) those local changes. The whole point of this skill is to
fast-forward to the latest `main` *without losing the personalization* and then get the app onto
the connected iPhone.

## Data-preserving bundle IDs

Do not install a physical-device build under the upstream `com.noopapp.*` product bundle IDs.
This local phone build must keep Muhammad Umer's personal namespace, or iOS will treat the app
as a different install and the existing local data container will not be used.

Expected local identifiers before `xcodegen generate`, build, or install:

- `bundleIdPrefix: com.mumer`
- `APP_GROUP_ID: group.com.mumer.noop`
- `PRODUCT_BUNDLE_IDENTIFIER: com.mumer.noop` for the app targets
- `PRODUCT_BUNDLE_IDENTIFIER: com.mumer.strandtests`
- `PRODUCT_BUNDLE_IDENTIFIER: com.mumer.noop.widgets`
- `PRODUCT_BUNDLE_IDENTIFIER: com.mumer.noop.watch`
- `PRODUCT_BUNDLE_IDENTIFIER: com.mumer.noop.watch.complications`
- `WKCompanionAppBundleIdentifier: com.mumer.noop` in `project.yml` and `NOOPWatch/Info.plist`
- Swift app-group fallbacks as `group.com.mumer.noop` in `WatchScoreSnapshot.swift` and
  `WidgetSnapshot.swift`

The only `com.noopapp` identifier that should remain in `project.yml` is
`com.noopapp.noop.debugexport`. If a pull resets any signed target to `com.noopapp.*`, change it
back to the matching `com.mumer.*` identifier before building or installing.

Read `references/context.md` for the why behind each decision (why xcstrings gets discarded, why
the Support card is re-derived rather than stashed, where the team ID comes from, why the
xcodeproj must be regenerated). Skim it the first time; the steps below are the operational core.

## Two kinds of local change — handled differently

**A. Carried diffs (stash → pull → pop).** Simple find/replace edits that almost never conflict,
so we stash them across the fast-forward and pop them back. This is the **personal-signing
rebrand** (`com.noopapp` → `com.mumer`), living in exactly these files:

- `project.yml` — bundle ID prefix, `APP_GROUP_ID`, every target's `PRODUCT_BUNDLE_IDENTIFIER`
  / `WKCompanionAppBundleIdentifier`. **One line stays `com.noopapp` on purpose:**
  `com.noopapp.noop.debugexport` — leave it.
- `NOOPWatch/Info.plist` — `WKCompanionAppBundleIdentifier`
- `Packages/StrandDesign/Sources/StrandDesign/WatchScoreSnapshot.swift` — `appGroupId`
- `StrandiOSShared/WidgetSnapshot.swift` — app-group `suiteName` fallback

**B. Re-derived patches (discard → pull → re-apply).** Code edits to files the team actively
changes, where carrying a stashed diff would conflict. We **discard them before the pull** (so the
pull is a clean fast-forward and brings upstream's version back), then **re-apply them fresh** on
the new code. This is the **home-screen "Support NOOP" card removal** in
`Strand/Screens/TodayView.swift` — see step 6 for exactly what to remove.

**Throwaway noise.** `Strand/Resources/Localizable.xcstrings` often shows a huge local diff that is
pure Xcode reformatting (`"key":` → `"key" :`, languages re-ordered) with no real content change.
Discard it — keeping it would clobber the team's translation work.

`Strand.xcodeproj` is generated by XcodeGen and gitignored; never hand-edit it.

## Steps

### 1. Assess where we are

```bash
git fetch origin
git rev-list --left-right --count origin/main...HEAD   # "<behind>  <ahead>"
git status --short
```

If `ahead` is 0 and `behind` > 0, the pull is a clean fast-forward (the normal case). If
`ahead` > 0 there are local commits — stop and ask the user how they want to integrate; don't
force a fast-forward.

### 2. Reset the files we re-derive or throw away (so the pull is clean)

These must be clean *before* the pull, either because they're noise or because we re-apply them
fresh afterward. Confirm each is only what you expect, then discard:

```bash
# xcstrings: confirm it's just reformatting (no real `value` changes), then discard.
git diff -- Strand/Resources/Localizable.xcstrings | head -40
git checkout -- Strand/Resources/Localizable.xcstrings

# TodayView: confirm the only local change is the Support-card removal (step 6), then discard it —
# it gets re-applied on the fresh upstream code after the pull.
git diff -- Strand/Screens/TodayView.swift | head -60
git checkout -- Strand/Screens/TodayView.swift
```

If either file has changes you don't recognize (real translation edits, or TodayView edits beyond
the Support removal), **stop and ask the user** — don't throw away real work.

### 3. Stash the rebrand, fast-forward, restore the rebrand

```bash
git stash push -m "personal-signing-rebrand com.mumer" -- \
  project.yml NOOPWatch/Info.plist \
  Packages/StrandDesign/Sources/StrandDesign/WatchScoreSnapshot.swift \
  StrandiOSShared/WidgetSnapshot.swift

git pull --ff-only origin main
git stash pop
```

`project.yml` usually auto-merges cleanly. If `stash pop` reports a conflict, the upstream
project.yml was restructured — re-apply the rebrand by replacing `com.noopapp` → `com.mumer`
in the bundle-ID lines (keeping `com.noopapp.noop.debugexport`), resolve by hand, `git stash drop`.

### 4. Verify the rebrand survived and is complete

```bash
grep -n "com.noopapp" project.yml   # expect ONLY: com.noopapp.noop.debugexport
grep -n "com.mumer"   project.yml   # expect bundleIdPrefix + APP_GROUP_ID + each target
```

Confirm the current expected local target identifiers are present:

- `com.mumer.noop`
- `com.mumer.strandtests`
- `com.mumer.noop.widgets`
- `com.mumer.noop.watch`
- `com.mumer.noop.watch.complications`
- `group.com.mumer.noop`

If upstream added a **new** target with a `com.noopapp.*` bundle ID, rebrand it to `com.mumer.*`
too (the stash couldn't know about brand-new lines).

### 5. Regenerate the xcodeproj

```bash
xcodegen generate
```

This must run after every project.yml change, otherwise the build uses a stale project.

### 6. Re-apply the home-screen "Support NOOP" removal

The team ships an in-content **Support card** on the iOS Today/home screen; this build removes it.
The pull just brought it back, so re-derive the removal on the fresh `Strand/Screens/TodayView.swift`.
Edits are by *intent*, not line numbers (the home screen moves around upstream):

1. **Remove the card from the iOS content flow.** Find the `#if os(iOS)` block in the Today
   `ScrollView`/`VStack` body that renders the support entry — it sits right after
   `DonationNudgeCard()` and renders something named like `supportRow`. Delete that
   `#if os(iOS) … supportRow … #endif` block (keep `DonationNudgeCard()` and `sourcesSection`).
2. **Remove the now-dead definition.** Delete the iOS-only `private var supportRow: some View { … }`
   (a `NoopCard` with a `heart.fill`, the text `"Support NOOP"` + "Donate or get in touch", and a
   chevron) along with its enclosing `#if os(iOS) … #endif`.
3. **Leave everything else.** Do NOT touch the **macOS** toolbar heart (`.toolbar { … "Support NOOP" }`),
   `SupportView`, `SupportModalOverlay`, or the `@State … showingSupport` / the iOS
   `.sheet(isPresented: $showingSupport) { SupportView() }`. Keeping the shared sheet wired up means
   `showingSupport` stays referenced (no unused warnings) and the card is a one-line restore later.
4. Update any now-stale comments that still describe an in-content iOS Support entry.

Sanity check after editing:

```bash
grep -n "supportRow" Strand/Screens/TodayView.swift   # expect: no code refs (comments are fine)
grep -n "Support NOOP" Strand/Screens/TodayView.swift # expect: only the macOS toolbar .help/.accessibilityLabel
```

If upstream has *already* removed the card (no `supportRow` to find), there's nothing to do — note
it and move on.

### 7. Resolve the signing team

`DEVELOPMENT_TEAM` is intentionally empty in `project.yml` (automatic signing). The working
team for the personal `com.mumer` build is **`625F56TE6C`** (Muhammad Umer personal team).
Confirm it's still the team the last on-device build used:

```bash
DD=$(find ~/Library/Developer/Xcode/DerivedData ~/Library/Developer/XcodeBuildMCP -path '*Debug-iphoneos/NOOP.app/embedded.mobileprovision' 2>/dev/null | head -1)
[ -n "$DD" ] && security cms -D -i "$DD" 2>/dev/null | plutil -extract TeamIdentifier xml1 -o - - | grep string
```

Use whatever team that profile reports (fall back to `625F56TE6C`). The profile
`iOS Team Provisioning Profile: com.mumer.noop` is auto-managed.

### 8. Find the connected physical device

```bash
xcrun devicectl list devices | grep -i physical
```

Pick the row that is **`connected` + `physical`**. Beware: simulators are often named
"iPhone 17 Pro" etc. — those are **not** the physical device. The real device here is
"Umer's iPhone". If the user names a model that doesn't match the connected physical device
(e.g. they say "17 Pro" but only a 16 Pro is plugged in), **flag the mismatch and confirm**
before spending a long build — there's usually only one physical device connected.

### 9. Build, install, and launch

Use the XcodeBuildMCP CLI (`xcodebuildmcp`, installed via Homebrew). The iOS app scheme is
`NOOPiOS`.

```bash
xcodebuildmcp device build-and-run \
  --project-path Strand.xcodeproj \
  --scheme NOOPiOS \
  --device-id <UDID-from-step-8> \
  --configuration Debug \
  --extra-args "-allowProvisioningUpdates" "DEVELOPMENT_TEAM=<team-from-step-7>"
```

This is a large project — the build can take a few minutes (longer on a fresh DerivedData).
Run it in the background and monitor the output file rather than blocking. Success ends with
`Build & Run complete`, the bundle ID `com.mumer.noop`, and a process ID — the app is now
running on the phone.

## After it's done

The normal resting state of the working tree is: the 4 rebrand files modified **and**
`Strand/Screens/TodayView.swift` modified (the Support-card removal). None of these are ever meant
to be committed. Don't commit or push anything unless the user asks. Report: which version you
pulled to (e.g. v7.4.0 → v7.5.0), that the rebrand was preserved, that the Support card was
re-removed, and the device it landed on.
