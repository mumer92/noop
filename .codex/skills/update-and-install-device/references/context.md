# Context & rationale

Background for the `update-and-install-device` skill — the *why* behind each step, so the
workflow can be adapted when reality differs from the happy path.

## Why the rebrand lives as uncommitted working-tree changes

The shared repo ships under `com.noopapp.*` bundle IDs and a `group.com.noopapp.noop` app
group, signed by the team. To build on a personal machine with a free/personal Apple ID, the
bundle IDs are rebranded to `com.mumer.*`. These edits are deliberately kept **uncommitted** so:

- `git push` never leaks them upstream, and
- pulling the team's latest `main` is a clean fast-forward instead of a merge of two histories.

`project.yml` even documents this: "Change it in this one place when building under your own
Apple ID." The app group ID flows from `$(APP_GROUP_ID)` into entitlements and Info.plist, and
is read at runtime via the `AppGroupIdentifier` Info.plist key (`WidgetSnapshot.suiteName`), so
the only Swift fallbacks that hard-code it are `WatchScoreSnapshot.appGroupId` and
`WidgetSnapshot.suiteName` — hence those two files are part of the rebrand set.

## Why `com.noopapp.noop.debugexport` stays

That identifier (in `project.yml`) is not a product bundle ID for a signed target — it's a
debug-export identifier that doesn't need to match the personal team. It was intentionally left
as `com.noopapp` in the original local setup; preserving it keeps the working tree faithful to
how the user had it.

## Why Localizable.xcstrings gets discarded

Opening the project in Xcode rewrites `Localizable.xcstrings` with its own formatter: a space
before every colon (`"key" :`) and languages re-ordered alphabetically (`de` before `en`).
That produces a massive diff (10k+ lines) with **zero semantic change**. Meanwhile upstream
ships real translation work (French, etc.) on this exact file across many commits. If the local
reformatting is stashed and popped, it conflicts catastrophically and, if resolved toward the
local side, silently reverts the team's translations. So: confirm the diff is pure reformatting,
then `git checkout --` it. If the diff contains real `value` changes, that's a different
situation — ask the user.

## Why the Support-card removal is re-derived, not stashed

The home-screen "Support NOOP" card lives in `Strand/Screens/TodayView.swift` — the Today screen,
which the team edits constantly. Two consequences:

- **Carrying it as a stashed diff would conflict.** Unlike the rebrand (mechanical find/replace on
  lines that rarely move), a code removal in a hot file will collide with upstream edits on almost
  every pull. So instead of stash→pop, we **discard the local removal before the pull** (clean
  fast-forward, upstream's card comes back) and **re-apply the removal fresh** on the new code.
  Re-deriving from intent is robust to the surrounding code shifting around.
- **It's idempotent and self-healing.** If upstream ever removes the card themselves, the re-apply
  step simply finds nothing to do. If they restructure it, we re-remove whatever the new entry
  point is by its intent (the in-content card that opens `SupportView`).

What the removal actually is (as of v7.5.0): on iOS the Today body rendered an in-content
`supportRow` right after `DonationNudgeCard()` — a `NoopCard` with a `heart.fill`, `"Support NOOP"`,
"Donate or get in touch — totally optional.", and a chevron — tapping it set `showingSupport = true`
to present `SupportView` as a sheet. The removal deletes that row's usage *and* its
`private var supportRow` definition (both iOS-only, `#if os(iOS)`), but deliberately leaves intact:

- the **macOS** toolbar heart (`.toolbar { ToolbarItem … "Support NOOP" }`) — macOS keeps its Support
  affordance;
- the shared `@State private var showingSupport`, `SupportView`, and `SupportModalOverlay`;
- the iOS `.sheet(isPresented: $showingSupport) { SupportView() }`, which keeps `showingSupport`
  referenced on iOS (so no unused-state warning) and leaves the feature a one-line restore.

This is a deliberate **UI personalization**, not a bug fix — don't try to "fix" it upstream or
commit it; it's a local-only preference, exactly like the signing rebrand.

## Why the xcodeproj must be regenerated

`Strand.xcodeproj` is generated by XcodeGen from `project.yml` and is gitignored (the `.gitignore`
keeps only the SPM `Package.resolved` and shared scheme data). After a pull changes `project.yml`
— or after the rebrand is re-applied — the on-disk `.xcodeproj` is stale until `xcodegen generate`
runs. Building without regenerating uses old bundle IDs / target settings.

## Signing: why DEVELOPMENT_TEAM is empty and where the real team comes from

`project.yml` keeps `DEVELOPMENT_TEAM: ""` and `CODE_SIGN_STYLE: Automatic` so the public repo
carries no one's team. For a **macOS** local build the repo uses ad-hoc signing (`CODE_SIGN_IDENTITY="-"`,
no team needed). For a **physical iOS device** you need a real team + provisioning, which Xcode
manages automatically once an Apple ID is signed in.

The working personal team is `625F56TE6C` ("Muhammad Umer"), discovered from the last on-device
build's `embedded.mobileprovision` (`TeamIdentifier`). The auto-managed profile is
`iOS Team Provisioning Profile: com.mumer.noop`. Passing `-allowProvisioningUpdates` lets
xcodebuild create/refresh that profile non-interactively; passing `DEVELOPMENT_TEAM=625F56TE6C`
tells automatic signing which team to use since the repo leaves it blank.

The keychain may hold more than one "Apple Development" identity (e.g. a second person). The team
ID from the last NOOP build's profile is the source of truth — don't guess from the keychain
parenthetical, which can differ from the team's 10-char ID.

## Bundle IDs are the app data boundary

The local phone install must keep the `com.mumer.*` product bundle IDs. Installing a build with
upstream `com.noopapp.*` product IDs creates or targets a different iOS app container, so the user's
existing local NOOP data will appear missing. Treat the current local identifiers as data-preserving
state, not cosmetic rebranding. After every pull, verify `project.yml`, `NOOPWatch/Info.plist`,
`WatchScoreSnapshot.swift`, and `WidgetSnapshot.swift` still use the current `com.mumer.*` and
`group.com.mumer.noop` values before building or installing.

## Device gotcha: simulators masquerade as the target model

`xcrun devicectl list devices` lists both physical devices and booted simulators. Simulators are
frequently named after newer models ("iPhone 17 Pro") and show `connected`, but their last column
says `simulated`. The physical phone here is "Umer's iPhone" (an iPhone 16 Pro, model `iPhone17,1`).
Always filter for `physical`, and if the user's stated model doesn't match the one physical device
that's plugged in, surface that before burning a multi-minute device build on the wrong assumption.
